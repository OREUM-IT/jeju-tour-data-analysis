# Linux 한 대의 Docker 운영 전환 계획

기준일: 2026-11-18 한국 시간. **Linux 호스트 한 대에서 시작하는 운영 설계다. Docker 이미지·Compose·실제 서버·DNS·터널·모델 추론을 구축하거나 운영 검증한 결과가 아니다.** 호스팅 업체·요금제·CPU/RAM·디스크·리전은 미선정이며 GPU는 API 모델 사용에 필수가 아니다.

현재 검증 기준은 [20 Langflow 로컬 안내](20-langflow-agent-builder.md)의 Langflow **1.13.3 패키지**다. 로컬 설치·버전 조회·MCP 세 도구 연결 결과를 운영 컨테이너 검증으로 확대하지 않는다. 같은 번호의 공식 Docker 이미지가 존재하거나 그대로 호환된다고 확인하지 않았다.

## 1. 현재 로컬 설정은 유지한다

- [langflow.env.example](../services/langflow/langflow.env.example)의 `LANGFLOW_HOST=127.0.0.1`, `LANGFLOW_AUTO_LOGIN=false`, `LANGFLOW_SSRF_ALLOWED_HOSTS=127.0.0.1`을 변경하지 않는다.
- 기존 로컬 MCP는 `127.0.0.1:8788`이며 `MCP_SERVICE_TOKEN` 인증을 유지한다.
- 운영 컨테이너 설정은 별도 파일·비밀 저장소·배포 단위로 준비한다. 현재 `.env`를 복사해 인터넷에 공개하지 않는다.
- 버전 선택 시 공식 보안 공지·수정 내역을 다시 확인한다. 문서에 기록된 버전만으로 향후 보안 상태를 보장하지 않는다.

## 2. 제안 배치와 구성별 책임

```text
기존 Vercel 서버 ── HTTPS + Access 서비스 인증 + 앱 인증 ──┐
                                                      ▼
Linux 호스트: cloudflared → 제한된 Agent Gateway → Langflow
                       │                       ├→ 제주 MCP → 장소 카탈로그
                       │                       └→ Langflow 전용 DB·볼륨
                       └→ 제주 MCP (직접 경로도 도구별 정책 검사 필요·미구현)
```

위 화살표는 허용할 통신 경로의 제안이다. Gateway는 **미구현**이며 현재 Langflow에 운영 권한 중계 기능이 이미 있다는 뜻이 아니다. MCP를 외부에서 직접 호출하는 경로와 Gateway에서 호출하는 경로 모두 서비스의 실제 도구 실행 지점에서 정책을 적용해야 한다.

| 구성 | 역할 | 공개·저장 경계 |
|---|---|---|
| Langflow | 운영자가 승인한 흐름 실행·편집 | 편집기와 원시 관리 API는 외부 공개 금지. 흐름·암호화 설정을 전용 DB/볼륨에 보존 |
| 제주 MCP | `places.search`, `places.get`, `constraints.check` | 읽기 도구 3개 유지. 카탈로그는 운영자가 지정한 읽기 전용 마운트 |
| Agent Gateway | 입력·사용자·도구 권한·시간/사용량 제한·결과 검증 | 구현 후 제한된 업무 경로만 허용. 임의 Langflow API 전달 프록시로 만들지 않음 |
| cloudflared | 승인된 호스트명을 내부 서비스에 연결 | 터널 자격 별도 관리. 외부 API 모델마다 인바운드 터널을 만들 필요 없음 |
| Langflow 전용 PostgreSQL | 흐름·사용자 설정 등 Langflow 상태 | 호스트·인터넷에 DB 포트 공개 금지. 앱의 회원·여행 DB와 분리 |

기존 앱 DB를 이 PostgreSQL로 이전하는 계획은 아니다. 데이터베이스·계정·볼륨·백업을 구분하고 Langflow가 기존 앱 DB의 관리자 자격을 공유하지 않게 한다. 실제 DB 연결 설정 이름·드라이버·마이그레이션은 선택한 Langflow 빌드에서 확인한다.

장소 저장소는 현재 JSON이며, 향후 PostgreSQL + pgvector를 후보로 검토한다. Langflow 전용 상태 DB와 관광 장소·근거·벡터의 논리 DB/계정을 분리한다. 벡터는 관련 후보 검색, 정형 데이터와 서버 검증은 사실·필수 조건 판정을 맡는다. 실제 벡터 인덱스·임베딩 모델은 아직 채택하거나 배포하지 않았다([22 보안 설계](22-jailbreak-and-prompt-injection-defense.md) 3절).

## 3. 컨테이너 바인딩과 호스트 포트는 다르다

| 대상 | 컨테이너 내부 리스닝 제안 | 호스트 공개 제안 |
|---|---|---|
| Langflow | 다른 허용 컨테이너가 접근해야 하면 `0.0.0.0:7860` | 관리용 `127.0.0.1:7860:7860`만 검토. 인터넷 인터페이스에는 publish하지 않음 |
| 제주 MCP | 별도 컨테이너에서는 `HOST=0.0.0.0`, `PORT=8788` 검토 | `ports` 없이 내부 Docker 네트워크로만 연결 |
| Agent Gateway | 검증한 내부 포트에 리스닝 | `ports` 없이 cloudflared가 내부 서비스명으로 연결 |
| PostgreSQL | 전용 DB 네트워크에서 필요한 연결만 수신 | `ports` 없이 Langflow에서만 접근 |

`0.0.0.0` 내부 바인딩은 해당 컨테이너의 인터페이스를 뜻한다. 호스트의 `0.0.0.0:포트:포트` publish는 외부 인터페이스에도 열 수 있으므로 같은 의미가 아니다. `expose`와 Docker 네트워크 연결 자체도 인증이나 세밀한 방화벽 정책을 대신하지 않는다.

각 컨테이너의 `localhost`는 **자기 컨테이너**다. Langflow에서 MCP로 가는 주소 후보는 `http://jeju-mcp:8788/mcp`이며 `http://127.0.0.1:8788/mcp`가 아니다. cloudflared도 별도 컨테이너라면 서비스명과 검증한 내부 포트를 사용한다. 이 주소 변경은 운영 검증이 끝난 별도 설정에만 적용한다.

Docker 네트워크는 필요한 서비스 조합으로 분리한다. DB 네트워크는 Langflow·DB에 한정하고, cloudflared가 DB에 직접 닿지 않도록 한다. Langflow의 외부 모델 호출과 cloudflared의 외향 연결은 필요한 목적지·프로토콜을 검증한다. 내부 전용 네트워크와 외향 연결이 필요한 네트워크를 구분한다.

## 4. 외부 공개보다 인증을 먼저 준비한다

1. `mcp.oreumit.com`, `agent.oreumit.com`은 **검증 후 사용할 후보**다. 현재 DNS·터널 배포 완료로 기록하지 않는다.
2. 공개 경로를 만들기 전에 해당 전체 호스트명의 Cloudflare Access 애플리케이션을 설정한다.
3. 서버 간 접근은 특정 서비스 토큰을 포함한 **Service Auth** 정책으로 제한한다. `Bypass`나 누구나 허용하는 정책으로 테스트하지 않는다.
4. Vercel 서버는 `CF-Access-Client-Id`, `CF-Access-Client-Secret`을 서버 비밀값에서 전달한다. 브라우저에 노출하지 않는다.
5. Access 검증과 origin 검증을 구성·시험한 뒤 named tunnel 경로를 연결한다. 원래 서비스로 Access를 우회할 공개 포트가 없어야 한다.
6. MCP의 별도 `MCP_SERVICE_TOKEN` 검사는 계속 유지한다. Gateway는 별도 앱 인증·요청 주체·권한·입력 검증을 구현해야 한다.

Cloudflare 서비스 토큰은 네트워크 진입 자격이지 여행자의 계정·코스 소유권이 아니다. 다른 사용자의 자료나 작업을 조회하지 못하도록 애플리케이션 권한을 별도로 검사한다. 공유 MCP 토큰만으로 사용자별 OAuth·scope·소유권 검사가 완료됐다고 표시하지 않는다.

Langflow 편집기는 운영자 SSH 포워딩을 통해 호스트 loopback에 접근하는 방식을 우선한다. SSH 키·접근자 제한과 Langflow 로그인 모두 유지한다. 외부 Gateway가 Langflow 관리·흐름 수정·API 키 관리 경로를 전달하지 않도록 명시적으로 차단한다.

## 5. 프롬프트 밖에서 도구 권한을 강제한다

Gateway에서 요청을 한 번 검사하는 것만으로 충분하지 않다. 모델의 도구 호출마다 **도구명·인자 schema·사용자 범위·허용 ID·남은 시간·사용량**을 실제 실행 직전에 검사한다. Langflow가 MCP를 직접 호출하는 경로에도 동일 정책이 적용되지 않으면 해당 경로는 운영 허용하지 않는다. 현재 흐름의 계산기·현재 날짜 같은 내장 도구도 목록에 포함해 검토하고 불필요하면 끈다. MCP 세 개만 제한해 전체 Agent 도구 허용 목록이 완성됐다고 간주하지 않는다.

현재 MCP의 세 도구·입력 검증·카탈로그 ID·근거 기반 `unknown` 처리는 유지한다. 이는 MCP 결과의 계약이며 모델의 최종 설명까지 자동 검증하지 않는다. Gateway는 최종 장소 ID·필수 제약·근거 인용을 별도로 검사해야 한다. 앞으로 개인 자료나 쓰기 도구를 추가할 때 서비스 자체의 권한·소유권 검사와 사용자 적용 절차를 구현한다. 모델이 만든 `approved=true`나 설명문은 권한이 아니다.

공개 요청자가 flow ID, 컴포넌트 코드, MCP 서버 URL, 도구 목록, 모델 ID, 비밀 변수, 내부 endpoint를 바꾸지 못하게 한다. 서버에서 승인된 흐름·모델·경로만 선택한다. 셸·임의 SQL·파일 경로·컨테이너 명령 도구를 추가하지 않는다.

검색 결과·MCP 출력·사용자 입력은 신뢰할 수 없는 데이터로 전달한다. 탈옥·프롬프트 주입 대응의 논문 근거·평가 범위와 정책 실패 시 동작은 [22 탈옥·프롬프트 주입 방어](22-jailbreak-and-prompt-injection-defense.md)와 함께 검토한다. 지정 논문은 공격 평가 연구이며 이 Docker 통제의 효과를 검증한 자료가 아니다. Docker 격리나 시스템 프롬프트 자체를 탈옥 방어 완료의 증거로 삼지 않는다.

## 6. SSRF 허용 목록은 도커에서 다시 검증한다

로컬에서 검증한 `LANGFLOW_SSRF_ALLOWED_HOSTS=127.0.0.1`을 도커 서비스명 허용 결과로 간주하지 않는다. 먼저 선택한 Langflow 빌드가 hostname과 최종 해결 IP를 어떻게 검사하는지 확인한다.

향후 `jeju-mcp` 같은 정확한 서비스명을 허용하려면 실제 DNS 해결·사설 IP 검사·연결·재시작 후 주소 변화·리다이렉트 동작을 시험한다. 이름만 허용했는데 IP 검사가 실패하면 그 원인을 확인하며 Docker 서브넷 전체 허용으로 해결하지 않는다.

임의 사설망 CIDR, `*`, 클라우드 metadata 주소, Docker host gateway 전체를 허용하지 않는다. 사용자가 목적지 URL을 제공하는 범용 HTTP 도구도 만들지 않는다. 허용되지 않은 호스트·IP·리다이렉트가 거부되는 음성 검사를 포함한다. 필요한 최소 예외를 입증할 수 없다면 운영 전환을 보류한다.

## 7. 이미지·컨테이너·비밀값 기준

- 실제 공식 이미지의 출처·존재·아키텍처·라이선스·취약점·기동을 확인한 뒤 **이미지 digest**를 고정한다. 검증하지 않은 Langflow/PostgreSQL/cloudflared 태그를 문서에서 만들어 넣지 않는다.
- 자체 MCP 이미지는 잠금파일과 검증한 Node 기반 이미지로 빌드하고 소스 커밋·이미지 digest를 기록한다. 개발 workspace나 호스트 홈 전체를 이미지에 포함하지 않는다.
- 가능한 구성은 non-root UID로 실행하고 capability를 제거하며 `no-new-privileges`를 적용한다. 실제 이미지의 권한 요구를 확인하지 않은 적용 완료 주장은 금지한다.
- 루트 파일시스템은 읽기 전용을 목표로 하되 DB 데이터·Langflow 필수 저장소·검증한 임시 경로만 별도 writable volume/tmpfs로 제공한다. 권한·마이그레이션·기동 검사를 통과해야 한다.
- **Docker socket을 어떤 Agent·Langflow·MCP 컨테이너에도 마운트하지 않는다.** privileged·host network·불필요한 host PID 공유도 사용하지 않는다.
- 모델/API 키, MCP 토큰, Access 토큰, DB 자격, Langflow 암호화 키는 서버 비밀 저장소 또는 제한된 비밀 파일로 공급한다. 이미지·Compose·흐름 export·로그에 값을 넣지 않는다.
- 키는 역할별로 분리하고 노출·만료에 대응해 회전한다. `LANGFLOW_SECRET_KEY`를 임의 교체하면 저장된 비밀값을 복호화하지 못할 수 있으므로 지원되는 교체·재암호화·복구 절차를 먼저 시험한다.
- CPU·메모리·PID·동시 요청·요청 본문·출력·실행 시간·로그 용량을 제한한다. OOM·큐 포화·디스크 부족 시 동작을 검증하며 restart policy만으로 복구를 보장하지 않는다.

## 8. 상태 점검·백업·롤백

`health`는 프로세스 생존이고 `ready`는 해당 업무의 처리 가능성이다. MCP의 `/healthz`와 인증된 `/readyz`를 구분한다. 현재 `/readyz`의 `productionReady:false`는 실제 카탈로그를 가져와도 유지되며 운영 준비 완료로 바꾸지 않는다.

Langflow 버전 응답만으로 DB 쓰기·모델 접근·MCP 실행 준비를 판정하지 않는다. Gateway readiness에는 승인 흐름·필수 의존성과 정책 로딩 상태를 포함하는 계약을 설계한다. liveness나 잦은 readiness 검사에서 유료 모델 추론을 실행하지 않는다.

Langflow 전용 DB는 일관된 DB 백업 절차를 사용하고, 필요한 볼륨·승인 흐름 export·설정 버전·이미지 digest를 함께 보존한다. 암호화 키는 백업 데이터와 접근 권한을 분리해 안전하게 복구할 수 있어야 한다. 기존 앱 DB의 백업은 별도 정책으로 유지한다.

백업 생성 성공과 복원 성공은 다르다. 별도 비공개 환경에서 DB·볼륨·암호화 비밀·흐름·MCP 인증 복원을 시험하고 복원 시각·손실 가능 범위를 기록한다. 보존 기간·복구 목표는 운영 요구를 확인한 뒤 정하며 아직 달성했다고 주장하지 않는다.

롤백은 이전 이미지뿐 아니라 흐름·설정·DB schema 호환성을 포함한다. 마이그레이션 전 백업과 복원 절차를 확보하고 신규 요청 유입을 차단한 뒤 호환된 이전 조합으로 되돌린다. 새 schema에 이전 이미지만 덮어씌우지 않는다. 기존 Vercel 추천 경로의 유지·복귀 동작도 확인한다.

## 9. 운영 전환 게이트

| 순서 | 통과해야 할 증거 |
|---|---|
| 1. 호스트·이미지 | Linux 사양·리전·접근자·업데이트 정책, 공식 이미지와 digest, 비밀값 주입·볼륨 권한 검증 |
| 2. 내부 기동 | non-root·제한된 파일시스템에서 Langflow/DB/MCP 기동, 서비스명 통신과 SSRF 허용/거부 검사 |
| 3. 업무 정책 | 제한 Gateway 구현, 실제 호출 지점의 권한·입력·출력·시간/예산·사용자 분리 검사 |
| 4. 외부 경계 | Access 먼저 설정, origin 우회 차단, 토큰 없음/오류/만료 거부, 허용 서버 요청만 성공 |
| 5. Agent 평가 | 허구·공개 fixture로 JSON·도구 왕복·근거·제약·주입 공격 검사, 정확한 모델과 사용량 기록 |
| 6. 운영 복구 | 부하·취소·재시작·OOM·디스크 부족·백업 복원·schema 호환 롤백 검사 |
| 7. 제한 연결 | Vercel Preview에서 기존 로그인·코스 저장 회귀 확인 후 승인된 범위로 운영 전환 |

위 게이트는 계획이며 통과 결과가 아니다. 비용·사양은 모델/동시성/자료량을 측정한 뒤 선택한다. 현재 로컬 환경과 설정은 유지하고, 운영 준비가 끝난 검토 가능한 구성만 별도 변경으로 적용한다.
