# 카탈로그 v2 Agent의 96문항 평가

기준일: 2026-11-19. **96문항 실측·채점을 완료했다: 정상 응답 73건, 실패 23건, 미실행 0건.** [PR #9](https://github.com/OREUM-IT/jeju-tour-data-analysis/pull/9)는 `main@4b41a03`에 병합됐고 이번 결과는 `codex/agent-v2-evaluation`의 [PR #10](https://github.com/OREUM-IT/jeju-tour-data-analysis/pull/10)에 있다. [27 문서](27-agent-catalog-v2-validation.md)의 981곳 카탈로그·최종 검증 흐름에 템플릿 요청 변환기와 별도 수집 모드를 연결했다. [채점 집계](../reports/baseline-langflow-v2-live-20261119.json)와 [런타임 감사](../reports/agent-v2-runtime-audit-20261119.json)를 별도로 보존한다.

허용 밖 ID는 줄었지만 전체 동작 정답은 기존과 같은 67/96이며 응답 완료율과 확인 고지율은 낮아졌다. 같은 장소 목록을 연결해도 관심 테마·걷기·날짜 충돌에 대한 요청 및 런타임 계약이 평가 기준과 완전히 일치하지 않는다. 전체 품질 개선이나 모델 우열로 해석하지 않는다.

이전 [Gemini 96시도·92응답·4실패](../reports/baseline-gemini-live-20261119.json)와 [Langflow v1 96시도·80응답·16실패](../reports/baseline-langflow-live-20261119.json), 합계 192시도는 변경하지 않는다. 27 문서의 실제 연결 확인 1건도 이번 96문항 배치와 별도다. 사람 검수는 0/24건, 합성 보안 사례 14개는 미실행이며 비용은 계속 미측정(`null`)이다.

현재 작업은 로컬 개발 환경에서 가능하다. 사용자 요청에 따라 운영 Linux 서버·cloudflared·Gateway 구축이 필요해지면 진행을 멈추고 필요한 범위를 알린다. 이번 평가를 운영 배포 승인으로 확대하지 않는다.

## 1. 평가하는 변경

| 항목 | 기존 Langflow 기준선 | 새 v2 평가 구성 |
|---|---|---|
| 장소 자료 | MCP v1 7,561곳 | 앱·평가셋과 같은 v2 981곳 |
| 모델 | Vertex AI `gemini-3.8-flash` | 같은 모델 |
| 입력 | 질의·문맥을 담은 자연어 래퍼 | 템플릿 질의·문맥에서 만든 엄격한 구조화 요청 |
| 출력 | 모델의 구조화 JSON을 그대로 채점 | 서버 Final Validator를 거친 최종 출력만 수집 |
| 실행 제한 | 이전 흐름 설정·공급자 60초·수집 HTTP 120초 | 새 Agent 90초·모델 최대 4회, 공급자·수집 제한은 별도 기록 |
| 실패 처리 | 이전 실행의 실패·미실행 기록 보존 | 새 실행에서 검증 차단·실행 실패도 분모에 보존 |

모델은 같고 새 v2는 평가셋과 같은 장소 목록을 사용하지만 입력 래퍼·구조화 필드·최종 검증·시간 및 호출 상한이 함께 달라진다. 이번 결과는 **현재 구성된 시스템의 결과**이며 모델 자체의 우열이나 각 변경의 단독 효과를 분리한 실험이 아니다. 이전 실패를 새 성공으로 덮어쓰지 않는다.

## 2. 정답을 사용하지 않는 요청 변환

요청 변환기의 API는 `buildValidatedRequest({query, context}, {catalog, requestId})`이며 Langflow 요청은 `buildValidatedLangflowRequest(input, {catalog, sessionId})`로 만든다. 계획의 `request.query`, `request.context`만 해석하고 카탈로그는 전체 형식 검사와 이름→ID 조회에 사용한다. 평가 문항 전체, 정답 동작·후보·근거, 별도로 저장된 조건 목록을 변환 입력으로 넘기지 않는다. 장소 이름 조회는 사용자가 질의에서 명시한 제외 대상을 완전 일치하는 유일한 ID로 옮기기 위한 것이며 정답 후보를 얻는 단계가 아니다.

변환기는 현재 템플릿의 문장과 조건절만 인식하는 닫힌 문법을 사용한다. 지정된 문법 밖의 문장을 유사하게 추정하거나 임의로 일부 조건을 지우지 않고 실행 전 오류로 남긴다. 템플릿 96개 변환 성공을 일반 한국어 자연어 해석 성공이나 작성 질의 지원으로 표시하지 않는다.

지원하는 내용을 런타임의 `filters`, `excludedIds`, `requirements`, 날짜 필드로 옮긴다. 런타임 `query`에는 기존 `formatBaselineMessage`로 원문 질의와 `today`·`timezone`·`forecast`·`trip` 문맥을 함께 보존한다. 구조화 필드에서 강제하지 못하는 문맥 조건도 이 래퍼에서 삭제하지 않는다. 정답의 예상 동작은 요청에 넣지 않는다. 요청 어댑터 버전은 `validated-template-v1`, 문법 버전은 `jeju-template-grammar-v1`이다.

## 3. 런타임이 강제하는 조건과 남는 한계

[27 문서](27-agent-catalog-v2-validation.md)의 최종 검증기는 원본 구조화 요청에서 후보와 필수 조건을 다시 계산한다. 지원 범위는 장소 분류·테마·권역·명시적 제외와 실내·영업시간·휠체어·예산 필수 조건이다. 실제 카탈로그의 `verified`와 비용 근거가 0이므로 자료 연결만으로 미확인 조건을 pass로 만들지 않는다.

다음 **6종은 `contextOnly`**다. 원문 질의에 남겨 모델이 읽게 하지만 런타임의 필터·필수 조건 검증이 모두 강제한다고 주장하지 않는다. 건수는 96개 템플릿 사전 변환에서 확인한 종류별 건수이며, 여러 종류가 한 문항에 함께 있을 수 있다.

| 종류 | 건수 | 강제 검증 범위 밖에 남는 내용 |
|---|---:|---|
| `theme_preference` | 16 | `해안 쪽으로`·`역사·문화·예술 쪽으로`처럼 관심 방향을 표현한 단일·복합 테마 선호 |
| `companion` | 7 | 동행자에 맞는 장소·동선 적합성 |
| `crowd_avoid` | 8 | 혼잡 회피·혼잡하지 않을 보장 |
| `transport` | 9 | 지정 이동수단의 실제 접근 가능성 |
| `walk` | 9 | 보행 부담·거리와 이에 따른 후보 제한 |
| `trip_dates` | 8 | 여행 기간과 방문일·숙박일수의 충돌 |

여행 날짜 충돌 8건은 방문일이 여행 기간 밖인 5건과 숙박일수 불일치 3건으로 로컬 감사에 기록한다. 이 감사 결과나 정답 `action`을 모델에 주입하지 않는다. 모델은 보존된 질의·문맥에서 스스로 처리하며, 검증기가 반드시 되묻게 만든 것으로 해석하지 않는다.

테마의 `contextOnly` 처리는 단일 필터 형식의 제약 때문만은 아니다. 이 닫힌 문법은 `해안 테마로`를 명시적 테마 필터로, `해안 쪽으로`를 관심 선호로 구분한다. 후자는 같은 단일 테마여도 필터로 승격하지 않는다. 이 선택 때문에 해당 문항의 후보 강제 범위가 평가 기준과 다를 수 있으며 점수 해석에 남긴다.

현재 런타임이 허용하는 `noticeTopics`는 다음 네 개뿐이다.

- `indoor_unverified`
- `hours_unverified`
- `wheelchair_unverified`
- `cost_unknown`

기존 평가셋에는 교통 접근·동행 적합성·걷기 거리·혼잡 보장 여부에 대한 확인 안내도 있다. 새 런타임의 네 주제만으로는 그 안내 점수의 모든 요구를 표현할 수 없다. 따라서 `accepted`가 모든 사용자 조건 충족이나 전체 평가 항목 통과를 뜻하지 않는다. 문맥 조건의 실패·낮은 안내 점수를 숨기지 않고 검증기 지원 범위와 함께 해석한다.

## 4. 명시적 수집 모드와 실행 전 검사

기존 수집기의 기본 모드는 `legacy`다. 새 흐름에는 **`--system langflow --request-mode langflow-v2`**를 명시하고 시스템 어댑터 버전은 `langflow-v2-1.0.0`으로 기록한다. 새 모드를 지정하지 않은 기존 Gemini·Langflow 실행을 자동으로 v2 요청으로 바꾸지 않는다. v2 모드는 Gemini 수집에 적용하지 않는다.

실행 전에 **전체 96문항**의 요청을 변환·검증하고, 하나라도 지원되지 않으면 일부 문항을 먼저 외부 모델에 보내지 않는다. 이 단계는 로컬 검사이며 실제 Google 추론 성공과 구분한다.

전송할 구조화 payload 전체의 정규화 해시와 카탈로그 해시·요청 어댑터·문법·흐름 버전을 실행 기록에 결합한다. 시도한 문항에는 `runtimeRequest`의 요청 ID·본문 해시·준비 요청 해시를, 계측 이벤트에는 세션 ID·결합 해시를 실패일 때도 남긴다. 재개 시 모드·카탈로그·전체 payload·시스템·엔드포인트가 일치해야 한다. v2 출력 선택자는 `outputIndex=0`, `ChatOutput-jejuV2`로 고정해 이전 캡처가 모두 실패여도 다른 노드로 재개할 수 없게 한다. 같은 원문 계획이라는 이유만으로 다른 구조화 요청이나 흐름을 섞지 않으며, 미실행 문항만 이어간다.

실행 명령은 기존 수집 명령에 새 요청 모드를 더한다. 아래 경로는 `services/jeju-mcp` 기준이며 인증값은 환경의 비밀 설정으로 공급한다. 실제 실행 전 고정된 흐름 ID·버전·출력 선택자와 새 파일 경로를 사용한다.

```sh
node scripts/collect-baseline-responses.mjs --execute \
  --catalog .local/agent-catalog-b0602a1.json \
  --set .local/evaluation-set-b0602a1.json \
  --plan .local/baseline-plan-b0602a1.json \
  --system langflow --request-mode langflow-v2 \
  --model gemini-3.8-flash \
  --prompt-version '<실제 v2 프롬프트 버전>' \
  --tool-version '<실제 v2 흐름·도구 버전>' \
  --endpoint 'http://127.0.0.1:7860/api/v1/run/<FLOW_ID>?stream=false' \
  --output-index 0 --component-id ChatOutput-jejuV2 \
  --max-cases 96 --timeout-ms 120000 \
  --output .local/langflow-v2-capture.json \
  --telemetry .local/langflow-v2-telemetry.json
```

`--set`은 기존 계획·채점 결합 확인에 쓰이며 요청 변환기에 평가 정답을 전달한다는 뜻이 아니다. 요청당 수집 HTTP 제한 120초와 Agent 내부 90초·모델 4회 제한은 서로 다른 범위다. 첫 오류에서 중단하며 자동 재시도하지 않는다. 재개할 때는 기존 `--resume-capture`, `--resume-telemetry` 쌍과 별도의 새 출력 경로를 지정한다.

이번 실제 배치는 비공개 조정기가 이 재개 기능을 사용해 **다음 미실행 문항만 순차적으로 이어간다.** CLI 자체의 첫 실패 중단 정책을 바꾸거나 실패 문항을 다시 호출하는 기능은 아니다. 매 재개 전에 Langflow 활성 작업 0과 등록 흐름·흐름 파일 해시의 불변을 확인하며, 예상하지 않은 HTTP 상태나 HTTP/시간 초과 실패가 3회 연속 발생하면 중단한다. 전체 상한은 문항당 한 번, 96문항이다. 매 실패를 사람이 수동 승인한 실행으로 표시하지 않으며, 실패의 읽기 전용 원인 검토는 별도로 진행한다. 모델·프롬프트·흐름 설정을 수집 중 바꾸지 않는다.

체크포인트는 각 시도가 끝난 뒤 저장한다. `SIGINT`·`SIGTERM` 처리는 있지만 프로세스나 환경이 강제로 사라지면 전송 중 문항이 파일에 기록되지 않을 수 있다. 이때 `not_executed`만 보고 공급자에게 한 번도 전송되지 않았다고 판단하지 않는다. 재개 전에 해당 세션·서버 작업·추적을 대조하고 중단 증거를 보존해야 한다. 재개 정책은 정확히 한 번의 과금을 보장하지 않으며 HTTP 시도 수와 Agent 내부 모델·도구 호출·SDK 재시도는 별개다.

## 5. 최종 출력과 실패 기록

수집 대상은 지정한 최종 ChatOutput이다. 내부 Agent 원문·추적·다른 노드 출력으로 대신하지 않는다. 최종 응답은 엄격한 순수 JSON 스키마와 요청 ID를 대조하고, 다른 문항의 응답을 붙이거나 빠진 ID·주장을 수정하지 않는다. 원문 보존 후 런타임 식별 필드 `schemaVersion`, `requestId`만 기존 채점 형식으로 변환하는 과정에서 분리한다. 의미·장소 ID·조건 주장은 그대로 채점하며 사람·모델의 사후 보정을 적용하지 않는다.

선택한 메시지에는 `properties.source.id: "JejuFinalValidation-v2"`, `properties.source.source: "Jeju Final Validation"`이 있어야 한다. 이 메타데이터는 최종 검증 컴포넌트의 식별자이며 Gemini 모델 이름이 아니다. 별도의 런타임 감사는 실행에 설정·기록된 모델·흐름을 확인한다. 감사의 `expectedModelCalls`는 해당 모델 이름으로 기록된 호출 span이고 `model.ok`는 저장된 span 상태다. 공급자 응답의 실제 모델 식별을 독립적으로 증명하거나 호출 성공을 보장하는 필드가 아니다. 모델·공급자 속성이 있고 상태가 `ok`여도 출력이 없는 실패가 있으므로 성공 응답 수는 최종 캡처의 엄격한 응답 검사로 확인한다.

감사의 `storedMessages.finalGate`는 Final Validator 출처로 저장된 메시지 수이며 **고정 차단 안내도 포함**한다. 이 값을 수락된 추천 수나 성공 응답 수로 사용하지 않는다. 저장 출처·실행 span 집계와 최종 캡처의 성공·실패 집계를 구분한다.

Final Validator가 차단한 결과와 HTTP·시간 제한·파싱 실패는 정상 추천으로 바꾸지 않는다. HTTP 200이라는 이유만으로 고정 차단 안내를 성공으로 채점하지 않는다. `RECOMMENDATION_BLOCKED`는 `invalid_output`과 `final_validation_blocked`, `VALIDATION_FAILED`는 `invalid_output`과 `final_validation_failed`로 기록한다. 나머지 v2 최종 계약 위반은 `invalid_validated_output`으로 구분한다. 거부된 원문은 비공개 계측 이벤트에 보존하고 실패·미실행 문항은 96개 분모에 남긴다.

Agent가 오류 원문을 제거하고 `AGENT_EXECUTION_FAILED`만 반환한 경우에는 확인 가능한 HTTP·출력 유무·도구 호출·경과 시간만 기록한다. 약 60초에 실패했다는 이유만으로 공급자 시간 초과·503·인증 오류라고 단정하지 않는다. 모델 호출 상한으로 나온 고정 문구가 JSON 계약을 어겨 최종 검증에서 막힌 경우도 공급자 장애와 구분한다.

캡처·payload·추적·문항별 점수는 `.local`에 저장하고 공개 보고서에는 집계만 남긴다. 비밀값·질의·장소 이름/ID·원문을 CLI 로그나 공개 PR에 출력하지 않는다. 비용은 실제 청구 근거를 확보하기 전까지 `null`로 유지한다.

1. PR #9의 최종 흐름·981곳 카탈로그와 별도 v2 MCP 서버를 확인한다. 기존 v1 서버·기준선 흐름은 보존한다.

### 7.1. 남은 후보·동작 계약 차이

허용 밖 ID 7개는 정상 응답 3건에서 나왔다. 한 응답의 5곳은 권역 필터를 통과했지만 평가의 주관심 테마 가중치 0.5 이상 기준에 못 미쳤다(0–0.4). 요청 변환기는 `쪽으로`라는 관심 선호를 `contextOnly`로 남기므로 런타임 테마 필터가 이를 강제하지 않았다. 나머지 2개는 최소 걷기 문항의 경로형 장소로, 런타임이 그 속성을 제외하지 않았다. 날짜 충돌은 이 ID 위반 5개의 원인이 아니다.

정상 응답의 동작 오류 6건은 날짜 충돌을 되묻지 않고 추천한 5건(여행 기간 밖 방문일 3건·숙박일수 불일치 2건), 최소 걷기 조건으로 경로형 장소를 제외하면 평가 후보가 비는 문항에서 추천한 1건이다. 날짜 충돌 5건에서는 불허 ID가 없었다. 원문 조건 보존 감사 96/96 통과는 명시 조건과 선호 문구가 남아 있다는 확인이며 **평가 후보 규칙·정답 동작과 런타임 계약의 일치 확인이 아니다.** 이 차이를 정답 입력이나 사후 응답 수정으로 감추지 않고 원래 점수를 유지한다.

확인 고지 17/31은 3절의 네 주제 제한과 함께 해석한다. 동행·교통·걷기·혼잡 등 원문에 남는 조건을 구조화 출력과 최종 검증이 충분히 표현하지 못한다.

## 8. 결과에 따라 이어갈 검증

실패 감사의 모델 호출 상한·검증 차단·Agent 오류 구분을 유지하고 후속 변경에서는 검색 인자와 호출 순서를 함께 확인한다. 검색 호출이 여러 번 있다는 사실만으로 같은 인자를 반복했다거나 무한 실행했다고 판단하지 않는다. 공급자 모델 성능이나 요금제 부족이라는 결론도 이 기록만으로 내리지 않는다.

후속 변경안은 **한 번의 후보 검색 → 후보별 조건 일괄 검사 → 최종 JSON**으로 도구 흐름을 제한해, 정해진 모델 호출 예산 안에서 마무리하도록 하는 것이다. 아직 구현·개선 효과를 검증한 변경이 아니며 최종 실패 감사에 근거해 별도 버전으로 검토한다. 관심 선호·최소 걷기·날짜 충돌의 입력 및 런타임 계약을 명확히 맞추고, 문맥 조건의 강제 범위와 네 확인 주제의 표현 한계를 보강해야 한다. 정답 후보를 런타임 입력으로 보내거나 기존 평가 규칙을 결과에 맞춰 바꾸지 않는다.

기존 Gemini 사람 24문항 검수와 합성 보안 사례 14개는 별도로 진행한다. 로컬 평가 이후 운영 Linux 서버·cloudflared·Gateway 구축이 필요하면 사용자에게 필요한 범위를 알리고 그 단계에서 멈춘다.
